# 第11章　数据加载与计算流水线

GPU利用率时高时低，常常意味着计算和等待正在交替。训练的一批数据可能经历远端读取、解压、解析、分词或图像增强、组批、主机内存缓冲、设备复制，最后才到前向传播。每个阶段都能形成瓶颈。数据流水线的目标，是让这些工作按正确依赖关系连续进行。

## 延迟与吞吐是两件事

假设准备一个批次需要30毫秒，复制需要8毫秒，GPU计算需要20毫秒。如果完全串行，一批需要58毫秒。理想流水线在不同批次之间重叠这三个阶段，经过填充后，稳态批次间隔下界是最慢阶段的30毫秒。第一批仍必须经过所有阶段，结束时也有排空成本。

这只是忽略资源竞争、缓冲限制和同步成本的教学模型。如果准备数据和复制同时争用主机内存带宽，真实时间可能更长。若把准备阶段降低到12毫秒，GPU计算可能成为新的瓶颈，此后继续增加数据加载线程便不会带来同样的收益。

因此，优化时先区分“单批多久完成”和“长期每秒处理多少批”。两个指标都重要，但不能用一个替代另一个。

## worker为何不是越多越好

PyTorch的`DataLoader`可以让多个worker进程提前准备数据。`num_workers=0`把加载留在主进程，便于调试；增加worker能并行处理解码和变换，但也增加进程、内存、进程间传递和调度开销。数据已在内存且变换很轻时，多进程甚至可能更慢。[1]

`persistent_workers=True`可避免每个epoch结束后重建worker，但worker持有的状态也会继续存活。`prefetch_factor`控制多进程加载时每个worker预取的批次数。假设4个worker各预取2批、每批占64 MiB，仅这些待取批次就可能约占512 MiB主机内存；实际还会有组批、中间结果和已交付批次。变长样本会让占用更加不稳定。[1]

对于迭代式数据集，多worker若没有正确划分数据，可能重复读取相同样本；分布式训练还需要在rank之间正确分片。加载更快但样本重复，已经改变了训练本身。性能指标应统计有效样本或有效token，而不只统计循环次数。

## 页锁定内存与异步复制

主机内存通常由操作系统按需管理；页锁定内存不被换出，能为设备直接搬运提供合适的缓冲区。`DataLoader(pin_memory=True)`让返回的批次进入此类内存，配合`to(device, non_blocking=True)`可减少主机等待，并为复制与计算重叠创造条件。[2]

```python
# 可运行模式：需安装 PyTorch；CUDA分支需要匹配的GPU环境。
import torch
from torch.utils.data import DataLoader, TensorDataset

if __name__ == "__main__":
    use_gpu = torch.cuda.is_available()
    device = "cuda" if use_gpu else "cpu"
    dataset = TensorDataset(torch.arange(4096).reshape(256, 16).float())
    loader = DataLoader(dataset, batch_size=32, num_workers=0,
                        pin_memory=use_gpu)
    total = torch.zeros((), device=device)
    for (batch,) in loader:
        batch = batch.to(device, non_blocking=use_gpu)
        total += batch.sum()
    print(total.cpu().item())
```

这段代码演示调用关系，没有承诺传输与计算已经重叠。若复制和计算都进入同一条流，它们通常按提交顺序执行。真正重叠还依赖独立流、硬件复制能力、足够的工作量，以及正确的事件依赖。[2]

也不要在热路径里对每个张量临时调用`pin_memory()`，再立刻上传；页锁定本身需要工作，可能抵消收益。异步传输期间，源缓冲区不能被过早改写，目标数据也不能在传输完成前被使用。为了速度省掉必要同步，会把偶发错误藏进数据管线。

## 变长数据如何浪费计算

训练语言模型时，同批样本常被补齐到最长长度。若三个样本分别有100、200、1000个token，统一补到1000，输入槽位中有1700个padding，实际token利用率约43%。按长度分桶、序列打包或可变长度内核，可能减少无效计算。

但打包不能只把文本拼起来。需要确定文档边界、位置编码、注意力掩码与损失掩码，使模型看到的训练目标符合预期。数据处理上的“优化”若让样本意外互相注意，改变的已是模型任务。性能与语义要同时验证。

对于视觉和多模态训练，解码、随机裁剪与多分辨率也会造成批次成本波动。可以记录每批有效token或像素、准备时间和GPU等待，找出长尾来源；只看全程平均值容易漏掉周期性停顿。

## 怎样找出真正的瓶颈

先用已在设备上的合成输入测量计算能力，再换为主机内存中的合成输入，最后接回真实数据。三种设置之间的差异帮助定位计算、传输、解码或存储的成本。合成数据的形状和分布仍要尽量接近真实工作负载，否则可能触发不同内核。

在Profiler时间线上同时观察CPU准备、内存复制与GPU内核。对比吞吐、主机内存、GPU空闲段和数据正确性，再逐次调整worker、预取或数据格式。最后以完整训练迭代验证收益。一个数据加载器单独测得很快，并不能保证与训练并发时同样快。[3]

## 预处理提前做，还是每次在线做

分词、格式校验和某些确定性解码可以提前离线处理，减少每次训练重复工作。这样通常会增加磁盘占用，并把分词器和预处理版本固定进数据产物。随机裁剪或动态掩码等操作若全部提前做，则可能减少训练中的随机变化，必须判断是否符合训练设计。

对于大型数据集，连续读取较大分片往往比海量小文件更容易保持吞吐，但分片太大又可能影响随机打乱、故障恢复和数据重新分配。一个合理方案通常同时记录分片标识、样本索引和随机种子，让吞吐改进与数据可追踪性共同成立。

数据搬到GPU后，也应减少不必要的主机同步。例如每个微小操作都读取设备标量打印，可能迫使CPU等待GPU完成，使本可连续提交的工作被切碎。日志可按固定间隔汇总，但汇总方式不能无意保留整张计算图。第12章将解释这种引用怎样推高显存。

观察训练曲线还要考虑数据顺序：按长度分桶若不再打乱，可能让短样本和长样本在时间上集中，改变梯度分布。于是一次“优化”同时改变了吞吐和采样。公平比较应保存采样策略，尽量控制其他条件，并用真实有效token统计收益。

还应观察预取队列是否持续为空或持续堆满。前者提示生产速度可能不足，后者可能说明消费者更慢或缓冲设置过大。单看队列长度不能定位全部原因，但结合批次时间能帮助判断调节方向。若加入缓存，需记录首次读取与热缓存两种状态；把已缓存的数据吞吐当成远端存储能力，会使后续容量规划失真。
