# 第15章　Eager、计算图与动态图

在 Python 里依次写下乘法、加法和激活函数，程序员看到的是几行语句。GPU 看到的是若干次内核启动、数据读写和依赖关系。计算图把这些操作及其关系显式表示出来，让系统有机会从更大的范围决定怎样执行。这里需要区分三种经常混在一起的对象：求导图、编译器计算图，以及设备执行图。

## 先理解立即执行

在 Eager 模式中，张量操作随着程序运行被调用。Python 可以读取外部状态、执行普通分支，也方便插入断点和检查中间值。对 GPU 而言，立即执行不意味着每个调用都等待设备完成；主机仍可能把工作异步提交给设备。[1]

例如 `z = torch.relu(x * scale + bias)`，从张量程序看是一条表达式，普通执行路径可能包含多个算子。若这些算子分别读取和写回中间结果，时间就包含计算、访存和启动开销。小张量尤其可能让启动和调度占据明显比例；大张量则可能主要受数据搬运约束。真正瓶颈仍需测量。

Eager 的优势是执行语义贴近程序控制流程。缺点是下一个算子出现以前，系统通常没有一个足够大的待优化区域。库可以把某些操作本身优化得很好，但跨越多个调用消除中间结果，需要更多程序信息。

## 求导图记录怎样反向计算

自动求导关心哪些结果依赖哪些输入，以及反向传播需要哪些中间值。若 `y=x*x`、`loss=y.sum()`，反向要把损失对 y 的梯度，沿乘法关系传回 x。这个记录为求导服务，不等于已经找到最快的内核组合。[2]

动态图通常指计算结构能够随实际程序执行建立。一次调用走了分支 A，另一次调用走分支 B，它们可以建立不同的求导关系。动态图不代表系统不能编译；编译器可以捕获一段实际执行的张量计算，再为适用条件生成执行方案。

也不要把“静态图”简单理解为输入尺寸永远固定。图可以包含符号维度、结构化条件或循环；而某些使用动态图接口的程序，也可能在长时间训练中始终走相同结构。图的建立方式、控制流表达能力和形状是否动态，是几个独立问题。

## 编译图让系统看见更大的计算区域

编译器可以分析 `multiply → add → relu` 的依赖，发现前两步结果只被下一步消费，于是考虑融合。它也可以推断某个转置是否只改变索引，选择库调用，或者为特定布局生成代码。图给出优化的可能性，具体变换仍受算子语义、硬件资源和后端实现约束。[3]

捕获图通常需要建立“这份方案何时有效”的条件。例如输入 dtype、设备、形状、步幅或某个 Python 配置值改变时，原方案可能需要重新检查。所谓特化，就是针对满足某些条件的情况做更具体的优化。特化越深入，潜在优化空间可能越大，可复用范围却可能缩小。

考虑一个按阈值选择激活函数的模型。如果阈值是固定的 Python 配置，编译时可能只保留选中的分支。如果条件依赖运行时张量值，就必须表达这种数据依赖控制流，或在边界回到 Python。两种写法表面上都有 `if`，对编译的要求却不同。

## 设备执行图解决另一层开销

CUDA Graph 等设备执行图机制捕获一组已经确定的设备操作及依赖，再以较少主机调度开销重放。它主要改变提交和执行组织，不自动等同于跨算子生成一个融合内核。一个程序可以既经过编译器优化，又把优化后的执行序列放入设备执行图。[4]

可以用两项独立问题区分：编译器在问“这些计算能否重写成更合适的程序”；设备执行图在问“这串设备工作能否更有效地反复提交”。二者可能共同减少开销，但各自的约束、内存行为和调试方式不同。

## 给小 Transformer 选择边界

训练循环包含读文件、分词、搬运数据、模型计算、损失、反向、优化器和日志。将它们全部想象成一张巨图，通常不利于理解。更实用的起点是固定一个可重复的模型计算区域，把复杂的输入处理和低频日志留在边界之外。

首先在 Eager 模式确认模型正确。再选择主要计算区域做编译，比较输出、梯度和训练过程；最后才观察是否值得扩展到优化器或更多训练步骤。现代框架的可编译范围在变化，因此边界应按实测与版本确定，不能把某一代工具的限制写成永久规则。

## 一个无需 GPU 的观察

本章随附 `examples/15-fx-graph.py` 使用 `torch.fx.symbolic_trace` 查看简单模块的图。它用于观察节点、输入和依赖；FX 符号追踪与 `torch.compile` 的 Dynamo 捕获路径并不相同，不能把这个实验当作完整编译流程模拟。[5]

运行后，找到乘法、加法和 ReLU 对应的节点，再看每个节点使用谁的结果。接着把中间值额外返回，思考它为什么可能影响融合：既然调用者要观察该值，系统就不能总把它当作完全不需要保存的内部临时量。

理解计算图以后，性能问题就能分层描述：是 Python 调度过多，是图被频繁切碎，是生成的内核不好，还是底层库调用已经接近瓶颈？这些问题需要不同工具，也会导向不同改动。

## 图上的边也有大小与寿命

画计算图时，常用箭头表示依赖，却容易漏掉箭头代表的实际张量。若两条分支共同使用同一个大张量，它必须活到最后一个消费者用完；若一个中间值只用于求导，即使前向已经经过它，也可能继续占据空间。给箭头标上形状、dtype 和最后使用位置，计算图就会同时成为显存分析工具。

例如 A 产生一个 64 MB 的结果，B 使用后又交给 C，D 还要独立使用它。即使 B 已执行完，也不能因为“下一步到了 C”就回收 A 的结果；必须等 D 不再需要，或选择在 D 使用前重算。执行顺序由此影响峰值显存。编译调度、重计算和内存复用看起来是不同技术，实际都在处理依赖与存活区间。

检查图时，还可以标出哪些操作只能发生在主机、哪些提交给设备。两者之间若需要读取真实张量值，执行就可能必须等待设备。画出这个等待点，比仅在图上统计节点数量，更能说明为什么一个很小的日志操作也会影响训练时序。
