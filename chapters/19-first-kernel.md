# 第19章　第一个 Kernel 与可靠计时

模型训练慢了，最先需要的通常是一把可靠的尺子。写出一个运行在 GPU 上的函数并不困难，困难在于确认它完成了什么、是否算对，以及时间到底花在哪里。本章选择向量加法：输入两个长度相同的数组，逐项相加。它没有复杂数学，能让我们专心观察一次内核启动。

## 从算子到一批工作

设两个输入为 $x$、$y$，输出满足 $z_i=x_i+y_i$。框架中的一次加法叫作算子；实际执行的设备程序叫作内核。一个算子可以启动多个内核，一个融合内核也可以实现多个算子的组合。不要把 Python 的一行代码当成 GPU 上的一条指令。

这里每个输出只依赖同一位置的两个输入，因此不同位置能够独立计算。主机端负责准备数据、分配输出、决定启动多少工作；设备端负责读取、相加、写回。输出数组应在计时前准备好，否则测量中会混入内存分配成本。输入也先放到设备上，另做包含数据传输的端到端测量。[1]

先在 CPU 上写参考实现，再编写内核。参考实现的作用是定义语义：输入类型是什么，允许哪些形状，是否支持不连续内存，遇到空数组怎么办。对于第一版，我们主动限定为同设备、同长度的一维连续 FP32 张量。输出还必须拥有独立存储，不能与任一输入共享底层存储。即使两个一维切片都是连续的，它们也可能部分重叠；一个程序写回输出时，可能覆盖另一个程序尚未读取的输入。示例通过比较底层存储起始地址保守拒绝共享存储，这也会拒绝同一存储内实际上不重叠的非空切片。空输入不启动内核。[4] 限制写清楚，比悄悄对某些输入算错更有价值。

## 把长度分成块，处理最后一截

假设每个程序实例负责 256 个元素。长度为 1000 时，启动数是向上取整的 $\lceil1000/256\rceil=4$。前三块处理 768 项，最后一块只剩 232 项，却仍然拥有 256 个逻辑位置。因此，读写都必须使用 `索引 < 1000` 的掩码。

只对写操作加掩码是不够的：越界读取已经发生，结果即使没有写回，也可能触发非法访问。反过来，只限制读取、却将填充值写到越界地址，同样错误。用整齐的 1024 项测试，很容易掩盖这个问题。应额外检查 1、255、257、1000 等长度；空输入直接返回空输出，不启动零工作量网格。

本书的 `examples/19-vector-add-triton.py` 给出了完整 GPU 实验，包含输入约束、尾部掩码、参考结果与计时。它需要可用的 PyTorch、Triton 和受支持 GPU；交付环境没有这些设备条件，因此没有将示例输出写成实测成绩。读者应在自己的目标环境运行。[2]

## 为什么普通秒表可能量错

GPU 启动通常是异步的。CPU 把任务交给设备队列后，就能继续执行下一行。如果用 Python 秒表包住一次调用，往往主要量到提交开销；下一次读取结果时才发生等待，成本被记到了别处。

有两种常用测法。第一种在测量前后同步设备，用主机时钟测整个区间，适合观察提交加执行的整体成本。第二种在同一设备流上放置开始和结束事件，等待结束事件完成后读取事件间隔，适合观察设备时间。[3] 这两种时间回答不同问题，报告时应说明。

```python
# PyTorch 风格的设备事件计时；先确保工作运行在同一流。
for _ in range(20):
    launch()
torch.cuda.synchronize()
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
start.record()
for _ in range(100):
    launch()
end.record()
end.synchronize()
ms_per_call = start.elapsed_time(end) / 100
```

重复次数有两个用途：降低时钟噪声，并减少单次启动过短带来的计量误差。它不意味着后面的 100 次代表训练中的 100 个真实批次。反复访问相同地址可能命中缓存，与大规模流式数据不同；主机提交不够快时，设备事件区间也可能包含排队空隙。极短内核可另测图重放，但要标出测量模式，不能把图重放与普通启动混作一组比较。

## 先把冷启动单独拿出来

第一次调用可能创建上下文、加载设备代码、即时编译、选择算法或分配缓存。Triton 的不同特化参数还可能触发新编译。若研究交互式延迟，冷启动很重要；若研究稳定训练吞吐量，应该先完成预热，再计时。不能把首次调用删掉后仍把结果叫作“首次响应时间”。

一次完整记录至少包括 GPU 型号、驱动与框架版本、数据类型、长度、块大小、预热次数、重复次数，以及计时是否包含分配、复制和编译。共享设备上还有别的任务时，噪声不是代码优化能消除的。多轮测量报告中位数或分位数，比挑最快的一次更可信。

## 用流量解释结果

FP32 加法每项读取两个 4 字节输入、写入一个 4 字节输出，逻辑流量为 12 字节。对 $N$ 项，若设备时间为 $t$ 秒，可以计算 $12N/t$ 字节每秒。这里算的是由算子语义得到的有效带宽，不是硬件计数器测到的实际 HBM 流量。

例如，**假设** 100 万项加法用了 20 微秒，则有效带宽为 600 GB/s。这个数字只是算术例子，不能当成本书硬件成绩。小数组可能主要受启动成本影响；中等数组可能被缓存影响；足够大的数组才更接近持续显存带宽问题。向量加法的运算量低，即使减少一条加法指令，也不一定缩短总时间。

最后，把这份内核放回训练：若它只占一步训练时间的 1%，即使变快一倍，整步也只减少约 0.5%。最初的成功标准应当是“语义明确、边界正确、测量可信”，然后才轮到追求局部速度。

## 一次只改变一个实验条件

建立基线之后，可以固定长度与数据类型，只修改每块负责的元素数，例如从 128 改成 256、512。每次都先对照结果，再测时间；如果同时修改数据类型、长度和启动方式，即使观察到变快，也很难解释原因。接着固定块大小扫描输入长度，观察耗时是否先近乎平坦、后来随数据量增长。这能帮助区分启动主导与流量主导的区间。

还可以在固定长度下比较两种用法：重复写同一输出，以及循环使用多组输入输出。后者增加总工作集，更接近一些流式场景，却同时改变了地址复用和主机管理成本。实验记录应把这个变化写出来。有效带宽出现异常高值时，先检查缓存、计时单位和同步位置，不要立即解释成显卡超过物理极限。

如果程序报错的位置似乎与出错内核无关，也要想到异步执行。非法访问可能在后续同步或复制时才被报告。调试时可以缩小到最小输入，在可疑调用之后显式等待，并使用目标平台的检查工具；性能测量时再恢复正常执行方式。调试同步和生产执行可以采用不同策略，但两者都需要清楚的记录。
