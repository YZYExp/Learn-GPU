# 第6章　线程、Warp 与 SM：GPU 如何组织工作

要把一百万个数分别乘以二，不必在 GPU 上创建一百万个独占核心。程序描述大量逻辑工作，硬件再把它们分组、驻留和调度。逻辑线程、调度分组和物理执行资源属于不同层次；把它们分清楚，才能理解并行度、分支与占用率。

## 从工作编号到线程块

以 CUDA 的一维启动为例，程序把工作组织为网格（grid），网格含多个线程块（thread block），每块含多个线程。线程通常用块编号与块内编号计算全局索引：

$$
i=\text{blockIdx.x}\times\text{blockDim.x}+\text{threadIdx.x}.
$$

假设有 1000 个元素，每块 256 个线程，需要向上取整为 4 个块，共 1024 个逻辑线程。最后 24 个线程没有对应元素，必须检查 `i < 1000` 后再读写。数据规模不整除块大小是正常输入，不应只在测试时选整齐尺寸掩盖问题。[1]

这些编号描述“谁处理什么”，不承诺某个线程永久占住某个算术单元。线程块也不按块编号保证执行顺序。通常应让不同块能够独立运行；如果依赖一个块先完成、另一个块再读取，却没有正确的跨块机制，就可能出现不稳定甚至死锁。

## SM 是承载工作的硬件单元

NVIDIA GPU 包含多个流式多处理器（Streaming Multiprocessor，SM）。线程块被分配到 SM 上，所需线程状态、寄存器和共享内存等资源要能在该 SM 的限制内安排。一个 SM 可以驻留多个块，也可能因资源占用较高而只能驻留少数块。[2]

块内线程可以使用共享内存协作，并在允许的位置通过屏障同步。这让分块矩阵乘法成为可能：先把一块输入搬到片上，再让多个线程复用。但是屏障不能随意放入只有部分线程会到达的分支；参与范围与执行条件必须符合 API 约束。

现代 CUDA 还存在协作组、线程块集群等扩展能力，在特定硬件和启动约束下扩大协作范围。它们不是普通网格默认具有的保证。入门阶段先掌握块内协作、块间独立，后面再按明确机制建立更大范围的数据交换。

## Warp 让一组线程共同发出工作

NVIDIA 当前 CUDA 执行模型中的 warp 包含 32 个线程，线程在 warp 内的编号称为 lane。硬件按这样的分组组织许多指令执行；SIMT，即单指令、多线程，允许程序员使用线程语义，同时利用相似指令的数据并行。[2]

若一个 warp 的所有线程走同一条路径，执行资源较容易有效利用。若一部分线程做 A、另一部分做 B，硬件可能分段执行不同路径，并通过活动掩码控制哪些 lane 生效。分歧的代价依赖路径长度、数据和具体实现，不能简单说“出现一次 if 就慢一半”。按块边界一致地分支，也与同一 warp 内交错分支不同。

从 Volta 开始的独立线程调度改变了若干执行细节，但它没有赋予程序“无需同步就能安全共享数据”的权利。依赖旧式隐含 warp 同步的代码可能不正确；warp 级交换与同步应使用相应原语并给出正确参与掩码。[2] 因而 warp 既是性能分析的重要对象，也不是可以绕过内存模型的借口。

## 为什么大量驻留工作能隐藏等待

GPU 执行一次显存读取时，结果可能不能立刻回来。SM 若有其他已就绪的 warp，就可以发出别的工作，而不必让所有执行资源等这一份数据。这种利用多个工作组覆盖等待的方式，称为延迟隐藏。

**占用率**通常表示实际驻留的 warp 数与该硬件可支持最大驻留 warp 数的比值。它由线程块尺寸、寄存器、共享内存以及硬件上限共同影响。若每个线程使用更多寄存器，单个线程的局部计算可能更高效，却会挤掉其他驻留工作；若分块太小，又可能缺少数据复用。[3]

因此占用率不是越高越好。一个高效矩阵内核可能用较多寄存器与共享内存换取复用，在中等占用率下仍然更快。降低寄存器上限也可能导致寄存器溢出到更慢的存储，反而增加访问成本。正确目标是缩短任务时间，在可解释的资源取舍中找平衡。

## AMD 的对应概念不能机械改名

HIP 的网格、块和线程接口与 CUDA 接近，便于表达同类工作，但硬件组织不是逐项相等。AMD 常用工作项（work-item）、工作组（workgroup）、波前（wavefront）和计算单元（CU）等术语；编译器与具体架构决定实际映射。

特别要注意 wavefront 大小。AMD CDNA 计算架构通常采用 wave64；RDNA 系列常以 wave32 工作，部分架构和编译模式还支持 wave64。应查目标 GPU 与编译配置，不能写死“AMD 永远是 64”，也不能把 CUDA 的 32 位 lane 掩码直接照搬到所有 HIP 场景。[4]

SM 与 CU 都承担执行与片上资源管理，但数量、发射方式、矩阵单元和寄存器组织不同。拿一家的“核心数”与另一家的“CU 数”直接相除，没有明确比较意义。跨厂商移植要保留算法语义，再重新核查分组、同步、寻址与资源使用。

## 用三个层次检查一个内核

先看逻辑映射：哪些元素由哪个线程或数据块处理，边界有没有覆盖。再看协作范围：谁共享数据，谁必须等待，参与者是否一致。最后看资源和调度：是否有足够工作、是否发生严重分歧、片上资源是否限制驻留。

本章可以手工为 1000 个元素、256 线程每块的例子列出四块的有效索引区间。再想象将访问改成每个线程跨很远读取，或让相邻 lane 走不同长路径。即使还没有运行 GPU，也能先分辨正确性问题与性能问题；真正的快慢留给后续的编译与测量确认。

## 并发不保证同时完成

一个网格可以包含比硬件驻留能力多得多的线程块。假设某台设备在所用资源配置下只能同时驻留 16 个块，而任务启动 160 个块，这些块将分批获得资源。程序仍具有 160 块的逻辑并行性，但某一时刻并不是所有块都活跃。这个教学数字只用于说明调度关系，不对应特定 GPU 的规格。

因此，跨块等待尤其危险：如果当前驻留块不断等待尚未被调度的块，后者又因为资源被占满而无法开始，就可能互相卡住。常用做法是让一个内核产生局部结果，再在有明确顺序的后续内核中合并；若使用设备级协作机制，则必须满足其启动与同步条件。把算法拆成多个阶段有时正是为了正确表达全局依赖，启动次数少并不自动代表设计更好。
